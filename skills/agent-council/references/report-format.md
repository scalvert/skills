# Report Format

Standard structure for multi-agent evaluation panel reports. Write to a file (`eval-[subject]-results.md`) rather than as inline chat output — these reports are long and need to be reference documents.

---

## Report File Structure

```markdown
# [Subject] — Evaluation Panel Results

**Assessment Date:** YYYY-MM-DD
**Version Assessed:** [version or commit]
**Assessment Method:** N-agent parallel panel with cross-panel discussion round
**Use Case Evaluated:** [the specific deployment scenario being assessed]

---

## Executive Summary

[2-3 paragraphs. Cover: overall verdict, the most important finding, what works well, what doesn't, and a recommended path forward. Be direct — the executive summary is what stakeholders read.]

**Verdict by use case:**
| Use Case | Readiness | Score |
|---|---|---|
| [Use case A] | Ready / Not ready / Conditional | X/10 |
| [Use case B] | Ready / Not ready / Conditional | X/10 |

---

## Panel Scores (Post-Discussion)

| Agent | Domain | Initial | Final | Delta |
|---|---|---|---|---|
| `agent-name` | Domain description | X.X | X.X | ±X.X |
| ... | | | | |

[Note if all revisions went in one direction — "All agents revised downward in the discussion round" is itself a finding.]

---

## Section 1: Critical Issues (P0 — Will Cause Failures)

Each P0 issue should have:
- **Issue title** (plain language)
- **Confirmed by:** which agents (in parentheses after: number of agents)
- **File:** exact file path and line number
- Code snippet showing the problem (when useful)
- What the correct behavior should be
- **Fix:** specific, actionable one-sentence fix

---

## Section 2: Significant Issues (P1 — Should Fix)

Same format as P0, abbreviated. These won't cause immediate failures but will be problems in production.

---

## Section 3: [Domain-Specific Sections]

Group related issues by domain when there are enough to warrant it:
- Eval Methodology Issues
- Remote Server Reliability Gaps
- Security Issues
- Developer Experience Issues
- Test Coverage Gaps

---

## Section 4: Project Health Issues (P2-P3)

Non-code concerns: bus factor, versioning, documentation drift, dependency health.

---

## Section 5: Alternatives Assessment

| Alternative | [Key capability A] | [Key capability B] | Maturity | Adoption Effort |
|---|---|---|---|---|
| [Alt 1] | Yes/No/Partial | Yes/No/Partial | High/Med/Low | Low/Med/High |

Include:
- When to use each alternative
- What the subject does that alternatives don't
- Revised recommendation after panel discussion

---
```

## Severity Definitions

| Severity | Definition | Example |
|---|---|---|
| **Critical** | Will cause observable failures in production use | Auth silently dropped on SSE fallback |
| **High** | Will cause problems under realistic conditions or in specific scenarios | No retry logic against flaky remote servers |
| **Medium** | Causes friction, poor UX, or misleads users without failing | Config option that validates but does nothing |
| **Low** | Clean code concern, future risk, or minor inconsistency | Client version hardcoded to stale value |

**P0**: Critical and High issues that block the stated use case
**P1**: Issues that affect production reliability or trustworthiness
**P2**: DX, test coverage, and quality-of-life issues
**P3**: Nice-to-have improvements

---

## Writing the Executive Summary

The executive summary should answer these questions:
1. Can the stated use case be done with this subject today? (Yes/No/Conditionally)
2. What is the single most important finding?
3. What genuinely works well? (Credibility requires balance)
4. What's the recommended path forward?

Avoid hedging language ("it might be possible to...") and avoid boosterism ("this is excellent for..."). State the verdict directly.

---

## Distinguishing Analysis from Opinion

In the issue descriptions:
- **Analysis**: "The SSE fallback at `clientFactory.ts:131` does not pass `authProvider` — confirmed by reading the constructor call, which takes `{requestInit}` without the `authProvider` option present in the Streamable HTTP path at line 123."
- **Opinion**: "The SSE transport seems like it might not handle auth correctly."

All Critical and High issues should have analysis-grade descriptions with file:line references. Medium and Low issues may use shorter descriptions.

---

## Report Length Guidance

- **Executive summary**: 200-400 words
- **Per-issue description**: 50-150 words for P0/P1; 25-75 words for P2/P3
- **Summary table**: All issues, one line each
- **Total report**: No fixed limit; completeness matters more than brevity for a reference document

Write for two audiences:
1. **Decision-maker (reads exec summary + table)**: Should know the verdict in 3 minutes
2. **Engineer fixing issues (reads issue sections)**: Should know exactly what file to change and why
